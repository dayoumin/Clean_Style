Clean Style Multi User & Rate Limit

여러 사용자가 동시에 사용할 때의 동작, 비동기 처리, rate limit을 쉽게 정리한 문서

짧은 결론: 여러 사용자의 AI 대화가 서로 섞일 가능성은 낮습니다. 현재 채팅 API는 요청마다 독립적으로 처리되고, 대화 기록은 각 사용자의 브라우저 localStorage에 저장됩니다. AI 답변 생성 자체는 모델 제공사가 처리하고, Cloudflare Worker는 요청을 검증하고 AI 응답을 전달하는 중계 역할에 가깝습니다.

사용자가 많아지면 어디가 처리하나?

AI 제공사

답변 생성

실제 AI 계산은 OpenRouter 또는 NVIDIA 같은 모델 제공사가 처리합니다. 사용자가 많아질 때 가장 먼저 보는 것은 제공사의 요청 제한, 장애, 크레딧, 비용입니다.

Cloudflare

요청 중계

Cloudflare Worker는 질문을 받고, 프롬프트를 만들고, AI 응답 스트림을 사용자에게 전달합니다. 별도 서버를 직접 운영하는 구조보다 운영 부담은 낮습니다.

운영 주의

완전히 무제한은 아님

사용자가 아주 많아지면 AI 제공사 쿼터, 동시 스트림 수, 비용, rate limit 정책을 함께 봐야 합니다. 프로젝트 서버 CPU가 주 병목이 될 가능성은 낮지만 운영 한계가 없는 것은 아닙니다.

현재 다중 사용자 동작

괜찮음

대화가 섞이는 문제

서버가 사용자별 대화 내용을 전역 변수에 저장하지 않습니다. 사용자가 질문할 때마다 요청 body의 질문, 히스토리, 요약을 받아 그 요청 안에서만 처리합니다.

괜찮음

비동기 처리

여러 사용자의 요청은 동시에 들어올 수 있습니다. 각 요청은 자기만의 AI 스트림을 열고, 토큰을 받는 대로 해당 사용자에게만 전송합니다.

적용됨

요청 제한

현재 제한은 브라우저별 익명 clientId와 IP 전체 카운터를 함께 봅니다. 같은 Wi-Fi 사용자끼리 무조건 5회 제한을 공유하지 않도록 개선했습니다.

비동기식이라는 뜻

여기서 비동기식은 "한 사용자의 답변이 끝날 때까지 다른 사용자를 기다리게 하지 않는다"는 뜻입니다. 서버는 사용자 A의 AI 답변을 스트리밍하면서도 사용자 B의 요청을 별도로 받을 수 있습니다.

1. 사용자 입력

각 사용자가 자기 브라우저에서 질문을 보냅니다.

2. API 요청

/api/chat이 요청별로 질문과 대화 기록을 받습니다.

3. AI 호출

각 요청이 외부 AI API에 독립적으로 연결됩니다.

4. 스트리밍

답변 조각을 받는 대로 해당 사용자에게 전송합니다.

5. 브라우저 저장

대화 기록은 사용자 브라우저의 localStorage에 저장됩니다.

별도 대기열을 두는 구조는 아닙니다. 요청이 들어오면 즉시 처리하고, AI 제공자가 느리거나 막히면 그 요청만 느려집니다.

Rate Limit 쉽게 설명

rate limit은 "너무 많은 요청을 잠깐 막는 장치"

예를 들어 "1분에 5번까지만 AI 질문을 허용한다"는 규칙을 둡니다. 정상 사용자는 보통 걸리지 않지만, 새로고침을 반복하거나 자동 요청을 많이 보내면 잠시 막힙니다.

쉽게 말하면: 입구에서 "방금 1분 동안 이 출입구로 몇 번 들어왔는지" 세는 방식입니다.

너무 많이 들어오면 "잠시 후 다시 시도해주세요"라고 돌려보냅니다.

항목 현재 동작 의미
채팅 5회 / 1분 / 브라우저 + 200회 / 1분 / IP 개별 사용자의 반복 요청은 빠르게 막고, 같은 Wi-Fi나 기관망의 여러 사용자는 완충합니다.
결과 저장 5회 / 1분 / 브라우저 + 200회 / 1분 / IP 테스트 결과 저장은 보통 한 번만 발생하므로 브라우저별 반복 저장만 강하게 막습니다.
요약 20회 / 1분 / 브라우저 + 200회 / 1분 / IP 대화가 길어질 때 자동으로 호출되므로 채팅보다 높게 두되 API 카운터는 분리합니다.
저장 위치 서버 메모리 Map 간단하고 빠르지만, 영구 저장소는 아닙니다.

폰 사용자가 많을 때

대체로 괜찮음

개별 폰 + 모바일 데이터

사용자가 각자 휴대폰에서 모바일 데이터로 접속하면, 한 기관망 IP에 몰리는 상황보다는 제한에 걸릴 가능성이 낮습니다. 일반적인 개인 사용 패턴에서는 1분에 5번 AI 질문을 보내기도 어렵기 때문입니다.

상황에 따라 주의

단체 교육, 같은 Wi-Fi, 통신사 NAT

같은 강의장 Wi-Fi를 쓰거나, 통신사가 여러 휴대폰을 같은 공인 IP처럼 보이게 만들면 IP 전체 카운터는 공유됩니다. 다만 브라우저별 clientId를 함께 쓰므로 개별 사용자 제한과 단체 IP 제한을 나누어 볼 수 있습니다.

기관망만 문제가 되는 것은 아닙니다. 휴대폰 사용자가 많아도 같은 장소, 같은 Wi-Fi, 같은 통신사망 조건에서는 IP가 겹칠 수 있습니다. 현재 정책은 브라우저별 제한과 IP 전체 제한을 분리해 이 문제를 완화합니다.

Isolate란?

Cloudflare가 코드를 실행하는 작은 실행 공간

Cloudflare Workers는 요청을 처리하기 위해 작은 실행 공간을 여러 개 만들 수 있습니다. 이 실행 공간을 여기서는 isolate라고 보면 됩니다.

중요한 점은 isolate 안의 메모리는 데이터베이스가 아니라는 것입니다. 잠깐 유지될 수 있지만, Cloudflare가 새 isolate를 만들거나 기존 isolate를 버리면 메모리 안의 rate limit 카운터도 사라질 수 있습니다. 또한 카운터는 IP 전체 제한을 먼저 확인한 뒤 브라우저별 제한을 기록해, 사용자가 헤더 값을 계속 바꾸는 방식으로 메모리 키를 늘리는 문제를 줄입니다.

쉽게 말하면: 계산대가 여러 개 있는 매장과 비슷합니다.

각 계산대는 자기 앞에 온 손님 수를 기억하지만, 모든 계산대가 같은 장부를 보는 것은 아닙니다.

그래서 현재 rate limit은 "기본적인 과도 사용 방지"에는 좋지만, 아주 엄격한 사용자 제한 장치는 아닙니다.

이번에 적용한 개선점

적용됨

IP 하나만 기준으로 삼지 않기

여러 사용자가 같은 IP로 보이는 상황을 줄이려면 브라우저에 익명 clientId를 만들고, 서버에서 IP + clientId 조합으로 제한하는 방식이 더 현실적입니다. 현재 이 방식을 적용했습니다.

적용됨

API별 카운터 분리

채팅 요청과 결과 저장 요청은 성격이 다릅니다. 따라서 chat:..., results:...처럼 rate limit 카운터를 API별로 분리했습니다.

선택 사항

엄격한 제한이 필요하면 외부 저장소 사용

정말 정확한 제한이 필요하면 서버 메모리 대신 Cloudflare KV, Durable Object, D1 같은 공유 저장소를 사용할 수 있습니다. 지금 단계에서는 비용과 복잡도가 올라가므로 다음 할 일로 남겨둡니다. AI 제공사 예산 알림, WAF rate limiting, 접속 코드 또는 기관별 quota도 함께 검토 대상입니다.

권장 정책

대상 권장 제한 이유
개별 브라우저 5회 / 1분 일반 사용자는 충분히 쓰고, 자동 반복 질문은 빠르게 막습니다.
같은 IP 전체 100~200회 / 1분 단체 교육이나 같은 Wi-Fi 사용자를 한꺼번에 막지 않기 위한 완충 장치입니다.
결과 저장 5회 / 1분 / 브라우저 테스트 완료 저장은 반복될 일이 적고, 오남용 방지만 하면 됩니다.
최종 판단: 지금 구조는 다중 사용자 대화 분리에는 문제가 크지 않습니다. AI 답변 처리는 모델 제공사가 맡고, Cloudflare Worker는 요청 검증과 스트림 전달을 맡습니다. 현재는 clientId + IP 기준과 API별 카운터 분리를 적용한 상태입니다.
